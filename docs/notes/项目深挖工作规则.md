# 项目深挖工作规则

## 目的

本文件只约束“碳化硅外延层厚度确定研究”这个项目。它不是整个 vault 的全局规则。

## 当前项目节奏

这是一个科研型数学建模项目，不是一次性赶完的作业。推进时应保持慢、准、可追溯：

- 一段一段地产出结果。
- 每一段结果都要能被用户学习、消化、复用。
- 不为了显得推进很多而同时铺开太多文件。
- 不把旧论文当依据；旧论文只作为历史材料和反面诊断对象。
- 核心依据来自题目、附件数据、已核验文献、可复现实验和明确标注的假设。

## 工作方式

每一轮只做少量高价值事项，并在结束时写清：

- 本轮完成了什么。
- 产出了哪些文件。
- 哪些结论已经有证据。
- 哪些内容仍待核验。
- 下一轮最值得做什么。

## 禁止事项

- 不虚构文献、数据、实验结果、DOI 或资料来源。
- 不把只核验元数据的论文当作已读全文证据。
- 不删除原始资料。
- 不覆盖已有项目文件；若需要更新，追加新的“AI 深挖记录 - 日期”小节。
- 不把任务扩展成整个 Obsidian vault 建设。
- 不为了消耗额度重复总结。

## 优先事项

当前优先级如下：

1. 先把题目理解、问题拆解和建模路线打磨清楚。
2. 再做 Python 复现实验和模型修正。
3. 再进入 TMM / Airy 全谱拟合等复杂模型。
4. 最后回到论文写作和图表表达。

## 当前共识

- 后续代码全部使用 Python。
- 代码集中放在 `Code/`。
- 输出放在 `Experiments/outputs/` 和 `Experiments/figures/`。
- 交接信息必须及时更新到项目 `Handoff Note.md`。
- 项目推进以学习和研究质量为核心，而不是追求一次性完成。
- 后续文献原文、PDF、网页快照和附件优先进入 Zotero；本项目 vault 内只保留文献笔记、精读摘记、方法节点、引用追踪表和 Zotero 导入/核验状态记录。

## Zotero 文献管理规则

本项目后续采用 Zotero 作为文献原文和条目管理中心。vault 的职责是研究笔记，不再把新查到的文献原文长期堆放在项目目录中。

执行规则：

- 新查到的论文、标准、网页资料，优先建立 Zotero 条目，并在 Zotero 中保存 PDF、网页快照或链接。
- vault 中只写笔记：精读笔记、方法总结、引用追踪、模型来源说明、Zotero 待导入清单和已导入状态。
- 不直接编辑 Zotero 的 `zotero.sqlite` 数据库；导入应通过 Zotero 界面、Zotero Connector、RIS/BibTeX 导入文件、Better BibTeX 或 Zotero Web API 等安全方式完成。
- 若 Codex 当前不能直接调用 Zotero API，应先生成“待导入 Zotero 清单”，列出 DOI、题名、用途、是否已有 PDF、证据等级和下一步导入方式。
- 每篇进入论文正文的文献笔记应尽量记录 Zotero citekey、Zotero select URI 或 Zotero 条目链接；如果暂时没有，标记为“待补 Zotero 链接”。
- 已经保存在项目 `Sources/Literature/` 的旧 PDF 和网页缓存视为历史资料，不自动删除或移动；后续迁移到 Zotero 后，再由用户确认是否清理 vault 中的副本。
- 未全文精读的 Zotero 条目仍不能作为正文强证据；Zotero 只解决文献管理，不自动提高证据等级。

## 建模与调试过程记录规则

用户的核心目标是学习建模过程，而不是只得到最终答案。因此后续每一轮涉及模型、实验或代码时，必须留下过程记录：

- 写清本轮为什么选择这个模型，而不是只写模型名称。
- 写清输入、输出、变量、参数、假设和评价指标。
- 写清每一步公式的含义，并统一使用 LaTeX 格式，例如 $d$、$\nu$、$n(\nu)$、$\theta_0$。
- 推导类公式使用块级 LaTeX，例如：

$$
2 d n \cos\theta_1 \Delta \nu = m
$$

- 代码调试必须记录：检查了哪个脚本、发现了什么风险、是否运行、输出在哪里、哪些结果不能当最终结论。
- 如果模型失败或结果不稳定，也要记录失败原因；失败本身是研究证据。
- 每个阶段要区分“事实、推断、假设、待核验、下一步动作”。
- 不允许只给结论而省略思路；不允许把中间模型包装成最终模型。

## 公式显示规则

- 数学符号必须使用 LaTeX 口径记录，例如 $d$、$\nu$、$n(\nu)$、$k(\nu)$、$\theta_0$、$\theta_1$、$\Gamma_L$、$\Gamma_T$。
- 行内公式使用 `$...$`，块级公式使用 `$$...$$`。
- 不把公式写进 fenced code block；Obsidian 笔记应直接显示可渲染公式。
- 如果代码变量名和数学符号不同，笔记中要先写数学符号，再说明对应的 Python 变量名。
- 每次新增模型或实验后，优先同步 `Notes/数学符号与公式总表.md`，避免后续论文符号混乱。

## 学习导向输出规则

后续正式项目笔记应尽量包含以下结构：

1. 问题：本节要解决什么。
2. 思路：为什么这样建模。
3. 数学表达：变量、公式和 LaTeX 推导。
4. Python 实现：对应脚本、函数、输入输出。
5. 调试检查：单位、边界、异常、参数敏感性。
6. 当前结果：只写可追溯结果，不编造。
7. 不确定性：哪些内容还不能相信。
8. 下一步：最值得继续做什么。

## 模型完善过程主轴规则

本项目的研究过程文档、教程文档和论文草稿，必须以“模型如何逐步完善”为主轴，而不是以图表、引用或结果数字为主轴。

每一个模型阶段都应按下面的逻辑写清楚：

1. **为什么需要这个模型**：它是在解决上一个模型的哪个不足，例如峰距法太粗、FOD 只用极值、TMM 才能利用整条谱线。
2. **模型从哪里来**：说明它来自题目物理背景、基础光学推导、已精读文献、方法节点、数据现象，还是项目中的合理改造。
3. **核心假设是什么**：哪些是假设必须成立，哪些只是为了简化计算；这些假设可能带来什么误差。
4. **数学形式如何建立**：写出变量、参数、目标函数或约束，并用 LaTeX 解释公式每一项的意义。
5. **它比前一个模型多解释了什么**：例如从只解释条纹间距，升级到解释折射率色散、吸收、多光束干涉、双角度联合拟合或残差结构。
6. **如何用 Python 实现和调试**：写明对应脚本、输入数据、输出文件、运行结果和不能相信的部分。
7. **用哪些图表验证效果**：图表是模型验证的证据，不是叙事中心。必须说明每张图验证的是模型的哪一部分，例如周期稳定性、拟合质量、残差结构、敏感性或稳健性。
8. **验证后得到什么结论边界**：明确哪些结论已经比较可信，哪些只是候选点、局部最优或待核验推断。
9. **为什么进入下一步模型**：只有当当前模型暴露出明确不足时，才升级模型；不能为了显得高级而堆模型名。

研究过程文档应像“带详细推导和实验记录的最终论文底稿”：它可以比最终论文更啰嗦，但不能比最终论文更散。最终论文只保留必要论证；研究过程文档必须保留每一步为什么做、怎么做、如何验证、哪里仍不可信。

## 教程式图文讲解规则

面向用户学习的教程、研究过程文档和模型解释文档，必须优先服务“读懂”，而不是优先展示引用密度。

写作规则：

- 图表只是辅助理解和验证模型，不是研究叙事中心。不能把教程写成“看图集”；必须先讲模型的产生、公式、假设、实现和验证，再说明哪些图支持这些判断。
- 先像讲课一样解释问题、直觉、公式含义、图表怎么看，再在小节末尾放“学习链接（想回查时再看）”。
- 不在正文里把每一句都写成“某论文指出”；只有当公式、参数、数据或结论需要追溯时，才在学习链接中指向文献笔记、方法节点、代码或输出。
- 图表不能只嵌入不解释。每张关键图至少说明：这张图回答什么问题、横轴纵轴是什么、应该看什么现象、它支持什么结论、它不能证明什么。
- 对初学者不默认知道 FFT、FOD、TMM、RMSE、残差、自相关、介电函数等缩写；首次出现时必须用中文讲清楚。
- 能用图帮助理解的地方，优先嵌入已有可追溯图表；没有必要为装饰生成图片。
- 文献链接是为了让用户后续深入学习，不是替代解释。正文必须能独立读懂，链接用于核查来源和继续阅读。

## 总研究叙事规则

用户需要的是完整研究过程，而不是零散结论。因此后续每一阶段都要沉淀成可连续阅读的“研究叙事”：

- 要说明研究从哪里来、为什么进入这一步、这一步解决上一步的哪个不足。
- 要把数据处理、建模、实验、调试和论文表达连成一条线。
- 数据处理不能省略，至少记录数据来源、读取方式、清洗/筛选波段、异常与单位检查。
- 建模不能省略，至少记录模型假设、变量、公式、输入输出、评价指标和适用范围。
- 调试不能省略，至少记录运行环境、运行命令、失败或成功、输出文件、边界测试和不能相信的结果。
- 每当得到一个阶段性成果，主 agent 可以直接进入下一步，不必等待用户再次确认；但必须把“为什么进入下一步”写入过程记录。
- 过程记录要足够详细，让用户之后不看聊天记录也能理解项目整体思想。
- 对外输出可以简洁，但写入 vault 的研究过程要详细。
- 当上下文或额度接近限制时，优先更新 `Handoff Note.md` 和 `Notes/建模与调试过程记录.md`，保证下一位 agent 能继续。

## 研究方向自检规则

本项目推进一段时间后，必须主动检查研究方向，防止偏离核心目标。当前核心目标是：

$$
\text{构建一个更精确、更可解释的外延层厚度反演模型}
$$

并持续用题目数据、可复现实验、残差分析、敏感性分析和可视化图表去验证它。

每完成一组模型、实验、图表或论文内容后，必须做一次方向自检，至少回答：

1. 当前工作正在验证哪个核心问题？
2. 它是否服务于厚度反演模型的精度、稳定性、可解释性或论文表达？
3. 它使用的数据、模型、参数和图表是否可追溯？
4. 它是否只是增加文件数量，而没有提高模型可信度或用户理解？
5. 下一步是否应该继续沿当前方向，还是回到题目、数据、模型假设或文献依据重新校准？

如果某项工作不能明确回答上述问题，应停止扩展，回到以下主线之一：

- 题目与数据理解；
- 厚度反演模型建立；
- Python 可复现实验；
- 残差、敏感性、稳健性和不确定性分析；
- 论文结构、图表和可解释性表达；
- 文献来源与参数物理边界核验。

禁止为了显得研究很多而做无意义扩展，例如：

- 只生成漂亮图表但不解释它回答了什么模型问题；
- 只扩大参数搜索但不说明物理边界；
- 只堆叠模型名称但不比较假设、输入、输出和风险；
- 只写总结而不推进数据、模型、实验或论文质量；
- 偏离当前数学建模项目，转向无关的 vault 建设。

方向自检的结论应写入 `Notes/建模与调试过程记录.md` 或 `Notes/研究过程总览.md`。如果发现研究正在走偏，应明确写出“偏离风险”和“回到主线的下一步”。

## 算力与 token 成本提醒规则

本项目允许长期深挖，但不能默默消耗大量本地算力、上下文 token 或用户额度。后续 agent 在进入高成本任务前，必须先判断任务规模，并在成本明显升高时主动提醒用户考虑是否接入学校服务器或更合适的计算环境。

触发提醒的典型情况包括：

- 大规模全局优化，例如遗传算法、CMA-ES、粒子群、多起点非线性最小二乘或高分辨率参数扫描；
- 大量仿真谱生成，例如为机器学习初值模型、1D-CNN、MLP 或 surrogate model 批量生成训练数据；
- 大规模 bootstrap、MCMC、不确定性传播或灵敏度分析；
- 长时间批量 OCR、视频转写、文献图片解析或大规模文献精读摘要；
- 预计会占用大量上下文，需要反复读取长报告、长 PDF、长代码输出或多 agent 证据包；
- 本地运行时间、内存、依赖安装或网络下载规模已经明显超出一次普通建模实验。

默认策略：

1. 先在本地做小规模 sanity check，确认代码逻辑、数据流、单位和输出格式正确。
2. 如果小规模实验显示方向有价值，再估计扩大实验需要的时间、内存、token 和依赖。
3. 若成本较高，应暂停扩展并提示用户：可以继续本地小规模验证，也可以考虑接入学校服务器。
4. 不默认假设用户有服务器权限；只有用户明确希望接入时，才询问合法的 SSH、账号、队列系统或运行环境信息。
5. 不把服务器密码、长期 token、私钥或敏感登录信息写入 vault；如需连接，只使用用户明确提供且符合安全边界的临时方式。
6. 如果暂不接入服务器，应把实验降级为小样本、低分辨率、少轮次版本，并在记录中说明“这是缩小规模的验证，不是最终充分实验”。

这条规则服务于当前核心目标：

$$
\text{在可控成本内，构建更精确、更可解释、可复现的外延层厚度反演模型。}
$$

因此，提醒接入服务器不是为了追求更大的实验规模，而是为了避免在本地和对话上下文中低效消耗，同时保证模型、数据处理和可视化验证能够真正推进。
